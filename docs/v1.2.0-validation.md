# Drop v1.2.0 — validación de Collections

Fuente: `feature/v1.2.0-collections`. Último commit funcional antes de la
preparación de Release: `c97d2a7fa830421847f69bff7ac775d9eb5a4699`.

## Validación por bloques

- Block 1: esquema SQLite v2, migración v1 → v2, rollback y claves foráneas validados.
- Block 2: CRUD, memberships, normalización de nombres y observers validados.
- Block 3: interfaz y navegación de Collections validadas.
- Block 4: Release ARM64 e integración Swift/Expo validadas.
- Block 5: migración física de v1.1.0 (schema v1) a schema v2 en un Bundle ID
  de prueba, sin tocar la instalación estable de Drop.

La migración física preservó los tres LibraryItems: uno con progreso parcial,
uno con `completedAt` y otro sin progreso. Los hashes de Media y Artwork fueron
idénticos antes y después; inicialmente había cero Collections y cero
memberships.

Una build anterior al fix dejó una membership huérfana al eliminar una
Collection. La causa fue una conexión nueva de Expo SQLite para la transacción
exclusiva que no heredaba `PRAGMA foreign_keys=ON`. El commit
`c97d2a7fa830421847f69bff7ac775d9eb5a4699` activa y verifica las claves
foráneas en la conexión efectiva antes de iniciar la transacción. Los tests
automatizados posteriores, una Release ARM64 y el retest físico pasaron; no se
crearon nuevas memberships huérfanas. La única fila huérfana restante en la
app de prueba procede deliberadamente de la build defectuosa y se conservó
solo como evidencia.

El smoke test físico final pasó: crear una Collection, renombrarla con
Unicode/hanzi, añadir y quitar memberships, eliminar la Collection sin borrar
el LibraryItem, conservar cambios tras relanzar, eliminar un LibraryItem
dentro de una Collection, conservar una Collection vacía, verificar la cascade
LibraryItem → memberships y reproducir contenido tras la migración.

Resultado: **PASS**. Stable Drop: **no tocado**. Esta fue una validación del
autor; la verificación end-to-end independiente por terceros sigue pendiente.
